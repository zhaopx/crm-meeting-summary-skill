Object-first memory system

CRM Object Memory Design

这套设计先服务 CRM 对象本身，再服务 summary、判断、检索和后续动作。重点不是给 summary 补上下文，而是给每个对象建立自己的记忆层。

object-first today + long_term profile-first summary 只是消费方之一
当前页面只展示 memory 设计本体：对象是谁、今天记录什么、长期沉淀什么、CRM 事实何时进入 memory。消费规则放在后面，不反过来定义 memory。
Core map

核心总图

先定义对象，再定义每个对象的两层 memory，最后再决定哪些内容可被消费。

CRM Objects -> account -> opportunity -> contact -> person Each Object -> today -> long_term Each Layer -> object-specific fields
Time horizon

时间层

`today` 服务当前判断，`long_term` 服务长期解释。两层足够，不再拆 `short / mid / long`。

today

记录当前这次 interaction 后，对象今天的状态、信号、变化和风险。

long_term

记录跨多次互动后稳定下来的特性、偏好、模式和结构性背景。

Object scope

四类对象

Write rules

CRM 事实是否写入 memory

CRM 正常运营中的事实，不自动等于 memory。先判断这条事实是否改变对象状态，是否具有复用解释价值。

客户创建订单 -> 只写 CRM 商机阶段前进一次 -> CRM + today（如果改变当前推进状态） 新建一条销售记录 -> 只写 CRM 客户今天明确说先解决稳定性再谈续费 -> CRM + today 联系人多次要求先书面后开会 -> CRM + today，重复确认后可进 long_term 销售连续多次按时跟进承诺 -> CRM + today，稳定后可进 long_term
Promotion path

升级路径

所有信息先作为 CRM fact 存在。只有改变对象今天状态，或跨时间重复成立，才进入对象 memory。

CRM fact -> 不改变对象状态 只保留在 CRM -> 改变对象今天状态 写入 today -> 多次重复并稳定成立 升级为 long_term
Consumption boundary

使用边界

下面这些是消费规则，不是 memory 体系定义本身。memory 不覆盖当前证据，只补对象解释层。

1. 当前 meeting evidence 优先 2. 当前 CRM facts 次之 3. memory 不覆盖当前证据 4. 冲突时输出 memory_conflicts 5. today 服务当前状态判断 6. long_term 服务长期解释与模式补强
Red lines

红线

不能做什么

  • memory 不是会议纪要全文仓库
  • long_term 不能写单次即时状态
  • today 不是 raw notes 复制
  • 未确认的当前结论不能直接写死到 long_term

设计原则

重点：先定义对象记忆，再定义谁来消费它。
