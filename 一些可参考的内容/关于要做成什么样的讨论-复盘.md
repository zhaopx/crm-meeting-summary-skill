# 会议总结 Skill 讨论复盘与结论

来源：`关于要做成什么样的讨论.md`
范围：仅提取与“会议总结 skill 设计与方法论”相关内容，剔除入口/日程/在线会议集成等产品体验话题。

## 关键诉求（从讨论中抽取）

1. **不能用死模板**
   - 要给 AI 足够自由度，只提供“概要性指引”和“关注点清单”。
   - 目标是避免千篇一律与凑字段，保证每次会议输出贴合真实内容。

2. **必须有体系化方法论**
   - 不是点状优化或单个模板，而是能解释“为什么比飞书/钉钉强”的体系。
   - 需要清晰写出“流程 + knowhow + reference”如何协同。

3. **CRM 优势要落到上下文拼装**
   - CRM 的核心价值是更懂“客户、阶段、风险、关系”。
   - 必须显式纳入：客户/账户画像、商机阶段、赢单/续费关键风险与改进项。

4. **Reference 目录是核心资产**
   - 按“会议类型”建立 reference，而不是按固定模板。
   - 每个 reference 简短，强调“该关注什么、该补什么、该提醒什么”。

5. **Memory 是差异化引擎**
   - 不能等平台 memory，先用简单结构落地短/中/长期 memory。
   - 必须识别“参会人反复关注点”，并在总结里明确提示。

6. **流程 ≠ knowhow**
   - 流程是可执行 SOP，knowhow 是专业判断与关注点。
   - 必须区分并同时具备。

## 对当前流程的判断

### 已对齐
- 场景识别 → knowhow → 最小 CRM 补拉 → memory → 生成 → review 的主流程正确。
- 强调“不要限制模型能力，给自由度”的方向正确。
- 低置信度回退与最小读取原则正确。

### 不足与偏差
1. **CRM 上下文拼装公式未显式化**
   - 现在只是对象结构对齐，但未形成可执行的“拼装方法论”。

2. **Reference 体系颗粒度不足**
   - 当前按场景/行业，缺少按会议类型的简短 reference。

3. **Memory 还未成为硬规则**
   - 目前是“可用则用”，缺少“重复关注点必须显式输出”的约束。

4. **方法论文档缺失**
   - 没有一份“对外可读、可对比”的产品方法论文档。

## 结论

当前流程方向正确，但“比协同平台高一档”的核心方法论尚未落地。
需要补足：方法论文档 + reference 体系升级 + memory 强约束。

## 下一步建议（对齐讨论诉求）

1. 新增方法论主文档（解释 CRM 总结的核心优势与拼装公式）。
2. 升级 reference 体系：从场景扩展到会议类型，并明确关注点与补拉字段。
3. 强化 memory：把“重复关注点提醒”变成必输出项。
