# 场景 knowhow：需求澄清

版本: `v2`

## 这类会议的目的
这类会议的核心，不是把客户说过的话重新整理一遍，而是判断三件事：
1. 业务问题是否真实存在，而不是抽象兴趣
2. 问题是否足够重要，值得组织投入资源推动变化
3. 当前是否具备继续推进到方案、试点或立项阶段的最小条件

对 enterprise / B2B discovery 来说，高质量澄清会议真正要形成的，不是“客户有需求”这句空话，而是下面这条因果链是否开始闭合：

`当前痛点 → 业务影响 → 不行动后果 → 决策压力 → 推进条件 → 下一步 owner`

如果这条链没有闭合，会议再热闹，也不应被判断成高质量进展。

## 关注点
- 当前讨论的是业务问题本身，还是已经过早滑向产品演示和 feature 问答？
- 客户讲的是“想优化”，还是“必须解决”，两者的推进强度完全不同。
- 痛点是否有清晰的 current state 证据：流程卡点、效率损失、协同问题、数据断点、管理失控、客户流失、收入影响。
- 客户是否说清楚了受影响对象：哪个团队、哪类角色、哪段流程、哪个指标。
- 是否出现明确 urgency source：季度目标、上线节点、管理层要求、组织调整、业务增长瓶颈、替换旧系统窗口。
- 成功标准是否可以被验证，而不是停留在“更高效、更规范、更好管理”。
- 是否出现明确的决策链、预算路径、项目 owner、业务 owner、技术 owner。
- 下一步动作是在缩小真实不确定性，还是只是“再看看方案”。
- 当前客户 / opportunity stage 是否支持继续推进，还是讨论已经跑在 qualification reality 前面。

## 高价值正向信号
- 客户能清楚描述 current-state pain，且能落到具体流程、角色、场景，不只是泛泛说“效率低”。
- 痛点被连接到业务后果，如转化损失、跟进失控、预测不准、协同成本高、交付风险、管理不可见。
- 客户主动说出不行动成本或时间压力，说明 urgency 不是销售方单方面假设。
- 客户能定义 success criteria，例如响应时效、线索转化、商机推进率、流程可视化、数据完整性、管理动作闭环。
- 会议里出现了明确 owner：谁牵头评估、谁组织内部梳理、谁参与后续方案确认。
- 多个干系人从不同角度复述同一问题，说明痛点不是单人抱怨，而是组织级问题。
- 客户不仅问功能，还追问落地条件、数据准备、权限治理、实施路径、上线影响，说明已开始评估 change feasibility。
- 下一步是围绕关键不确定性展开，例如补 stakeholder map、确认 success criteria、梳理现状流程、补业务数据、锁评估范围。

## 高风险信号
- 客户大量提功能，但始终说不清业务问题和优先级。
- 会议中只有使用者表达兴趣，没有 owner、预算方、决策方或推动者出现。
- 讨论停留在“行业都这么做”“领导觉得要上系统”，但没有 current-state evidence。
- 所谓 urgency 只是“有空看看”“今年考虑下”，没有真实时间锚点。
- 客户说“都重要”，但无法说明 first use case 或优先级取舍。
- 成功标准模糊，导致后续任何方案都无法被判断为合格或不合格。
- 下一步只是“发个方案/约个演示/内部再看看”，但没有 owner、时间、验证目标。
- 客户反复回避现状数据、流程细节、参与人、决策路径，说明组织准备度不足或问题还未被内部承认。
- 当前机会阶段仍很早，但讨论已经超前进入实施级细节，说明 qualification 可能失真。

## 伪进展预警
以下信号除非有更强证据支撑，否则都视为弱信号：
- stakeholder enthusiasm，但没有 owner accountability
- 对 features 感兴趣，但问题并不紧迫
- 同意“看看 proposal”，但没有 success criteria 或下一次 checkpoint
- 参会人很多，但没有人明确承担推进责任
- 客户说“你们先整理一下材料”，但没有给评估边界或内部目标
- 讨论很多现状细节，但没有说明这些问题为什么现在必须被解决

这些都不等于 qualification 提升。真正有效的进展，应表现为：
- 问题定义更清楚
- 业务影响更具体
- urgency 来源更明确
- owner 与决策链更可见
- 下一步更接近 closing uncertainty，而不是制造更多表面动作

## 场景智慧：这类会议里真正要听什么
### 1. 听“痛点归属”，不是只听“痛点内容”
客户说“现在比较乱”“协同效率低”不够。要听的是：谁在为这个问题付代价，代价是什么，为什么现在开始不可接受。没有代价归属，痛点往往只是讨论素材，不是采购驱动力。

### 2. 听“紧迫性来源”，不是只听“想做优化”
真正能推动项目的紧迫性，通常来自外部窗口或内部压力：增长目标、季度考核、管理层要求、系统替换、组织变更、客户投诉、交付失控。若紧迫性只来自“大家都觉得应该升级”，推进概率通常偏低。

### 3. 听“谁能推动变化”，不是只听“谁在参会”
参会不等于承担责任。需求澄清阶段最关键的是识别：谁是业务 owner，谁是实际 champion，谁掌握预算或决策路径，谁会成为后续阻力。没有 change owner，再好的需求也容易停在会后。

### 4. 听“客户是在问能力，还是在找确定性”
如果客户持续追问落地方式、数据准备、系统边界、实施成本、风险控制，通常说明他不是单纯想听功能，而是在判断这件事能不能真正推进。此时会议意义已经从“兴趣验证”进入“可行性验证”。

### 5. 听“共识有没有扩散到组织层”
一个人觉得有问题，不等于组织准备行动。若多个角色从不同角度确认同一问题，且能对齐目标与后果，这才是高价值信号。否则需求容易停留在局部想法，难形成项目动力。

## 建议的下一步逻辑
优先选择能提升 qualification 质量、并缩小真实不确定性的动作。

推荐 next step 优先级：
1. 先补痛点定义：确认 current-state pain、受影响流程、业务后果
2. 再补 success criteria：明确什么叫“值得继续推进”
3. 再补 stakeholder 与决策路径：谁牵头、谁评估、谁拍板、谁可能阻塞
4. 最后才进入方案、试点或更深产品讨论

高质量 next step 应满足四个要素：
- 有明确 owner
- 有明确时间点
- 有明确要补齐的不确定性
- 有明确输出物或验证标准

如果下一步只有“发方案”“内部看看”“下次再聊”，则不应视为有效推进。
