# 场景 knowhow：项目交付 / 实施受阻与风险升级

版本: `v2`

## 这类会议的目的
这类会议的核心，不是判断“任务有没有在做”，而是判断**价值交付系统是否仍然可控**。

在 B2B SaaS / 企业软件实施里，真正决定项目成败的，通常不是某一个 bug、某一张排期表，甚至也不是某一个延期，而是下面四件事有没有同时成立：
- 业务目标是否仍然清晰且被持续对齐
- 范围、依赖、责任是否被真实治理
- 数据迁移、测试、cutover 是否有证据支撑，而不是口头乐观
- 当前执行风险是否已经外溢到客户信任、续约、扩单或管理层关注

这类会议要识别的本质是：项目是在**消化不确定性**，还是在**堆积未来爆点**。

## 关注点
- 当前讨论的是“任务进度”，还是“业务结果是否还能按预期落地”？
- sponsor / steering 层是否仍在有效介入，还是已经下沉成纯执行层自转？
- 关键风险是否被具体描述为 owner、触发条件、缓解动作、目标时间，而不是抽象抱怨？
- 范围变更是否经过明确取舍，还是在无治理地持续膨胀？
- 数据迁移、UAT、cutover 是否有可验证证据，还是只停留在“预计没问题”？
- 客户当前表达的是执行摩擦，还是已经升级为信任问题、管理问题、商业问题？
- 下一步动作是在降低不可逆风险，还是只是让团队看起来更忙？

## 高价值正向信号
- 业务目标、阶段目标、上线标准之间存在明确映射，不是各说各话
- sponsor 或关键决策人仍按节奏参与，并能对范围、优先级、资源做取舍
- 关键风险被写成可管理对象：owner、impact、trigger、mitigation、due date 清晰
- 依赖项有明确负责人，且 unblock path 已定义
- 范围变更有审批逻辑，团队知道哪些必须做，哪些可以延后
- UAT 讨论的是关键业务流程和验收标准，不只是零散功能点
- 数据迁移讨论包含映射、Mock / rehearsal、对账口径、异常修正机制
- cutover 讨论包含 go/no-go 条件、回退方案、窗口约束、现场支持安排
- 客户虽然承认有问题，但仍认可当前协同机制有效，未明显转向关系恶化

## 高风险信号
- 会议频繁复述“卡住了/还在推进/团队在跟”，但没有风险闭环信息
- sponsor 长时间缺席，关键决策持续下沉，项目只剩项目经理和执行层硬撑
- 范围一边膨胀，一边还试图保住原上线时间，没有明确 trade-off
- 依赖项很多，但 owner 不清楚，或 owner 无法调动资源
- timeline 被反复重申，却没有新的证据说明关键风险已下降
- UAT 仍停留在脚本执行层，没有回到 end-to-end 业务流程是否可跑通
- 数据迁移仍是“到时候再看/先上再修”，缺少 rehearsal、对账、异常回滚准备
- cutover 仍以经验判断为主，没有 go/no-go 标准和回退策略
- 客户开始把执行问题表述为“影响业务”“影响内部信心”“影响后续合作”
- 实施问题开始进入续约、扩单、付款、管理升级等商业语境

## 伪进展预警
以下信号除非有更强证据支撑，否则都视为弱信号：
- “我们已经开了很多会”
- “大家都很努力，开发做了很多”
- “客户这次语气还可以”
- “timeline 已经重新排过了”
- “已经列了很多 action items”
- “功能基本差不多了”

这些都不等于风险下降。真正有效的进展，应表现为：
- 关键阻塞被关闭
- 风险 owner 明确接手
- 对账、测试、演练有新证据
- 范围得到收敛
- 客户重新确认可接受的路径与标准

## 场景智慧：这类会议里真正要听什么
### 1. 听“问题定义”是否从技术问题升级成业务问题
当客户从“某个接口没通”“某个功能还没好”转为“这会影响上线”“这会影响业务切换”“这会影响内部推进”，说明问题已进入风险管理层，不再只是交付细节。

### 2. 听“谁在承担决策责任”
实施受阻时，最危险的不是没人干活，而是没人真正做取舍。会议里如果只有执行更新，没有 sponsor 决策、没有 owner 承诺，通常说明项目治理已经变薄。

### 3. 听“客户是在要解释，还是在要确定性”
客户重复追问 timeline、数据、切换、责任人，往往不是想听更多解释，而是在判断你们能否给出可依赖的确定性。

### 4. 听“情绪背后的商业含义”
当客户表达 frustration，不一定立刻代表关系失控；但如果 frustration 开始连接到内部 credibility、领导关注、续约或投资回报，就已经不是普通实施噪音，而是账户风险信号。

## 建议的下一步逻辑
优先顺序不是“谁声音大先解决谁”，而是**谁最可能造成不可逆后果先解决谁**。

推荐 next step 优先级：
1. 先确认 go/no-go 相关风险：哪些问题会直接阻断上线、业务切换或客户内部验收
2. 再锁定数据迁移、UAT、cutover 这三类高爆炸半径事项
3. 再处理 owner 缺失、依赖失控、scope creep 等治理问题
4. 最后才是一般性的协同优化、常规跟进和补充说明

高质量 next step 应满足四个要素：
- 有明确 owner
- 有明确截止时间
- 有明确验证标准
- 有明确升级路径

如果下一步只有“我们会跟进”“下周同步一下”“再内部看看”，则不应视为有效推进。
